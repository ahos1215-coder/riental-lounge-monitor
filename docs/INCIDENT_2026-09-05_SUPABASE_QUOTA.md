## 一行で

Supabase 無料プランの枠を超過し、**2026-09-05T22:06Z から全リクエストが HTTP 402 を返すようになった**。
そのまま **3日半**、利用者には「全42店 0人」という**誤情報**が表示され続け、混雑データ3夜分が恒久的に失われた。

## 2. 原因

### 2-1. 直接の違反

現在 Supabase が返す違反名は **`exceed_cached_egress_quota`**（cached egress の月間枠 5GB を超過）。
無料プランの枠は **cached egress 5GB/月・uncached egress 5GB/月・Storage 容量 1GB**。

### 2-2. 予告と実際の違反がズレていたこと（ここが最大の落とし穴）

- 2026-08-18 に受け取った予告は **Storage 容量 1GB 超過**についてのものだった。
- それに対して打った手（`cleanup_old_models.py`、2026-08-19）は **容量側だけの是正**だった。
- 実際に 9/5 に効いた制限で現在ブロックされているのは **egress（転送量）側**。
  **容量を直したから安心、と読んでしまった**のが 18日間の空白の中身である。
- なお、prune が実際に容量を枠内へ戻せていたかは Supabase 管理画面でしか確認できず、
  402 で管理 API も含めて照会できないため**未確認**（コード上は毎回の学習後に走る設計）。

### 2-3. egress を食っている実体（コードとローカルミラーからの実測・推定）

| 順位 | 消費源 | 量 | 対処の状態 |
|---|---|---|---|
| 1 | **Flask 起動時の42店モデル preload** | **1回あたり 34.1 MiB** | 内訳は `metadata.json` 320,848 B を**42回**ダウンロード（合計 12.85 MiB。うち**41回ぶん＝12.5 MiB、preload 全体の 37% が純粋な無駄**。1店目のぶんだけは必要な取得）＋ モデル84本 21.3 MiB。原因は `oriental/ml/model_registry.py::_load_single_unlocked` が店舗ごとに無条件で `metadata.json` を落としていたこと。1店目だけ sweep 経路に入って refresh 時刻を進めるため、残り41店が単店経路に落ちる。**→ 2026-09-09 に実装済み**（`_reusable_metadata()` が同じ refresh ウィンドウ内の metadata を使い回す。番犬 `tests/test_model_registry_metadata_reuse.py`） |
| 2 | **日次再学習でモデル名が変わる** | 84本 21.3 MiB / 日 | **設計どおり**（新しい世代を配信するために必要）。削減対象外。**枠を広げてもこの消費は残る** |
| 3 | **`/api/forecast_snapshot` / `/api/forecast_accuracy`** | 推定 **13〜17 MiB / 日** | `accuracy/snapshots/<date>.json`（全42店ぶん）を毎回丸ごと落として1店分だけ返しており、プロセス内キャッシュが無かった。`warm_cdn_local.py` が毎晩42回叩くので同じファイルを42回落としていた。**→ 2026-09-09 に実装済み**（`oriental/routes/forecast_accuracy.py` にプロセス内 TTL キャッシュ。形は `oriental/ml/forecast_service.py::_fetch_blend_weights` と同じ。キルスイッチは `FORECAST_ACCURACY_CACHE_TTL=0` / `FORECAST_ACCURACY_PAST_CACHE_TTL=0`。番犬 `tests/test_forecast_accuracy_storage_cache.py`） |

> **1と3の「実装済み」の意味を取り違えないこと。** 入っているのは**コード**であって、
> **削減効果はまだ本番で実測できていない**（402 のあいだは計測そのものができない）。
> 上の量はローカルミラーの実ファイルサイズからの積算＝**推定**である。
> 402 が解除されたら、Supabase 管理画面の egress 使用量を数日追って
> 「本当に減ったか」を確かめること（§5-1 の注意も参照）。

**ETag / If-None-Match による条件付き GET は使えない。** Supabase Storage が `If-None-Match` を評価せず
304 を返さない既知の未解決 issue（#60 / #193 / #267）がある。**実装しないこと。**

## 3. 影響

### 3-1. 利用者に見えたもの（これは「障害」ではなく**誤情報**である）

- `/stores` の**全42店が「男性0 / 女性0 / 計0」**。「空いている」と読める表示が3日半出続けた。
- **レポート84URL（daily 42 + weekly 42）が404**。
- 店舗ページの SSR が空箱。

「サイトが落ちている」なら利用者は諦めるが、「0人」は**信じてしまう**。
実害の性質が通常のダウンよりも悪い、という点をここに明記しておく。

> **404 になっていたのは当時の実装**（行が取れなければ一律 `notFound()`）。2026-09-09 に
> `frontend/src/lib/reports/reportAvailability.ts` を入れ、「取得できたうえで0件」だけを404、
> 「取りに行けなかった」は**404にせず「今だけ表示できません」を返す**ようにした。
> 次に同じことが起きたときの見え方はこちらになる（404 が CDN に焼き付く二次被害を避けるため）。

### 3-2. 恒久的に失われたもの

- **2026-09-06・09-07・09-08 の3夜分の混雑データ**。収集には後追いのキャッチアップ機構が無いため
  **遡及取得は不可能**。この3夜は今後どのモデル学習・精度検証からも永久に欠けたままになる。

### 3-3. 壊れなかったもの（fail-closed は全経路で効いていた）

**壊れた成果物が正規パスへ昇格した形跡はゼロ。** 具体的には:

- `scripts/snapshot_forecasts.py` — 規定数に満たない夜は `accuracy/snapshots/<date>.json` を上書きせず非ゼロ終了。
- `scripts/score_forecasts.py` — スナップショット不在を「no snapshot found」でアラートして exit 1。
- `blog_drafts` の carry-over — 失敗時は前回の良品本文・`is_published`・`target_date` を保持し、
  `error_message` は null のまま（＝読者に届く表示を壊さない）。
- ブレンド重みの凍結（`BLEND_WEIGHTS_MODE=frozen`）— 汚染なし。

**「空欄になった」のは正しい挙動であって、バグではない。** 嘘の数字を出さない代わりに欠測する、という
`CLAUDE.md` §3 の設計判断がそのとおりに働いた。

## 4. なぜ3日半も気づかなかったか

**検知は動いていた。通知が原因を運ばなかった。**

1. 収集ハートビート（`check-collection-heartbeat.yml`、2時間毎）は停止の**5時間後に赤くなり、以後16回連続で失敗し続けていた**。
2. しかし通知の実質的な出口が **GitHub の失敗メールだけ**で、そこには原因が一文字も載らない。
3. 同じ1つの原因が **9ワークフロー・49通**に増幅され、区別がつかないまま埋もれた。
4. 監視スクリプトは「照会失敗」時、detail を `_emit()` する前に `fetch_newest_ts` の中で
   `sys.exit(1)` していたため、**通知本文が空になっていた**。
5. しかもワークフロー側の固定文が挙げる原因は
   **「PC停止 / Render障害 / cron-job.org障害」の3つだけ**で、**今回の真因は候補に入っていなかった**。
   3つとも外れた通知が16回届いた。

6. **当時の** `/healthz` は `{"ok": True, ...}` と真偽値を定数で埋めて返すだけで、
   下流が全滅していても**常に200・常に `ok: true`** だった（warm-up 兼用のため200は意図的な設計）。
   外形監視5経路すべてが3日間**緑のまま**だった。`/readyz` は stale で503を返す実装があるが、
   どの監視も叩いていない。

> **4・5 は 2026-09-09 に修正済み**（別グループの作業。`scripts/monitor/_query_failure.py` を新設し、
> 照会失敗を `QueryFailed` で `main` まで持ち上げて detail と cause を必ず出す。ワークフローの
> `custom_body` は cause を優先し、特定できなかったときだけ従来の固定文に戻る）。
>
> **6 も 2026-09-09 に修正済み**（`oriental/routes/health.py`）。ただし直し方が重要で、
> **HTTP ステータスは意図的に200のまま**（`/healthz` は UptimeRobot の暖機口であり、
> Render 側のヘルスチェック設定がリポジトリから確認できない＝非200にすると本番が
> 再起動しかねないため）。**変わったのは本文**で、`ok` が実際の診断結果になり、
> `problems`（機械可読なコード配列）と `problem_detail`（そのまま通知に貼れる一文）が加わった。
> 今回の 402 なら `data_upstream_payment_required` と
> `Supabase /rest/v1/logs が HTTP 402 (...)` が本文に出る。
> **したがって「`/healthz` は使えない」はもう成り立たない。ステータスではなく本文を見ること**
> （§5-2 の1行目）。あわせて、利用者と同じ公開経路を外から叩く
> `.github/workflows/site-down-watch.yml`（30分毎）を新設した。

## 5. 復旧手順

### 5-1. オーナーにしかできない操作（**これをやらない限り何も直らない**）

コード側でできることは一つも無い。以下は Supabase 管理画面での操作で、**オーナー本人だけが実行できる**。

1. Supabase 管理画面 → 対象 Organization → **Billing**。
2. 次のどちらかで**即時に制限が解除される**:
   - **Pro プラン等への変更**（枠が広がる）、または
   - **Spend Cap の解除**（超過分を従量課金で受け入れる）。
3. どちらも選ばない場合は、**次の請求サイクルの開始まで復旧しない**（egress カウンタのリセット待ち）。
   その間ずっと 402 のままで、利用者には「全42店 0人」が出続ける。

> **注意**: §2-3 の削減2件（`metadata.json` の使い回しと答え合わせ系エンドポイントの TTL キャッシュ）は
> **2026-09-09 に実装済み**で、「消費源が手つかずのまま枠だけ広げる」状態ではない。
> ただし**効果はまだ本番で実測できていない**（402 のあいだは計測ができない）。
> また §2-3 の2位（日次再学習の 21.3 MiB/日）は設計どおり残るので、消費がゼロになるわけでもない。
> **枠を広げたら、Supabase 管理画面の egress 使用量を数日追って「本当に減ったか」を確かめること。**

### 5-2. 復旧後の確認手順（**この順番で**）

上から順に確認する。前の段が緑にならないうちに次を見ても意味がない。

| # | 見るもの | 具体的な確認 | 緑の条件 |
|---|---|---|---|
| 1 | **読み取り疎通** | **`/healthz` の「本文」を見る**。**HTTP ステータスでは判定しない**（暖機兼用のため意図的に常に200。§4-6）。本文の `ok` / `problems` / `problem_detail` が診断結果で、402 が続いていれば `data_upstream_payment_required` と `Supabase /rest/v1/logs が HTTP 402 (...)` が名指しで出る。裏取りは `/api/current?store=<1店>`。ステータスで判定したいなら `/readyz`（壊れていれば503） | `/healthz` の本文が `"ok": true` で `problems` が空。`/api/current` が 200 を返し中身が空でない |
| 2 | **モデルロード** | `/api/meta` の model 読み込み状況（`/healthz` と同じ形で返る）／`/api/forecast_today?store=<1店>` | モデルが読めており、予測が 503 でない |
| 3 | **収集再開** | cron-job.org が5分毎に叩いている。`/api/range?store=<1店>&limit=5` の最新 ts を**5〜10分あけて2回**見る | ts が前に進む。進まなければ cron-job.org 側の停止を疑う（自動再開しない可能性がある） |
| 4 | **表示復帰** | `/stores` を開く | 「0人」表示が消える。ISR/CDN キャッシュが残るので反映は遅れる。夜なら `MEGRIBI-warm-cdn` が温め直す |
| 5 | **レポート復帰** | `/reports/daily/<1店>` と `/reports/weekly/<1店>` を開く | **1〜5分（＋CDN伝播ぶん）で本文が戻る。** 404（や「今だけ表示できません」）だったのは行が消えたからではなく**読み取りが402で落ちていた**だけで、`blog_drafts` の行は §3-3 の carry-over で残っているため。ISR の再生成間隔は **daily = 60秒 / weekly = 300秒**（`frontend/src/app/reports/daily/[store_slug]/page.tsx:24` / `.../weekly/[store_slug]/page.tsx:31` の `export const revalidate`）。**戻ってくる本文の日付は障害前のまま**で、それは正常 |

> **§5-2 の5行目は、以前この記録が書き間違えていた箇所**（2026-09-09 中に訂正）。
> 旧記述は「次の生成便まで404のまま待つのが正常（weekly は次の水曜まで）」だったが、
> それを信じると **weekly は最大6日間、本物の二次障害を『正常』と誤認して見逃す**。
> 正しくは次の2段階に分けて見る:
> - **本文が戻るか** … 402 解除から **1〜5分**。戻らなければ**別の異常**（行そのものの消失、
>   ビルド／デプロイ事故、`BACKEND_URL` や Supabase 資格情報の設定崩れ）として調べること。
> - **日付が最新になるか** … **次の生成便**（daily = 当日 18:00 / 21:30 JST、
>   weekly = 次の水曜 06:30 JST）。ここを待つのは正常で、手動で急ぐ必要はない。

**やらなくてよいこと**: 3夜分の欠測を埋めようとしないこと（遡及取得の手段は無い）。
snapshot / scores の空欄も埋めないこと（§3-3 のとおり、空欄が正しい記録）。

## 6. 教訓

1. **予告には期限がある。期限を持つ予告は、期限を過ぎたら誰かが必ず見る場所に置く。**
   今回の予告はスクリプトの docstring と環境変数リファレンスという、**普段誰も読まない場所**にしか無かった。
   「書いた」＝「対処された」ではない。
2. **予告の文言をそのまま鵜呑みにして、隣の枠を見なかった。**
   容量の予告 → 容量だけ直した → 実際に効いたのは egress。無料プランの枠は
   cached egress / uncached egress / Storage 容量の**3本ある**。1本の話が来たら残り2本も見ること。
3. **「検知した」と「気づいた」は別。** 16回連続で失敗し続けていたのに、原因を運ばない通知は情報ゼロと同じ。
   通知本文に**原因**（今回なら 402 と `exceed_cached_egress_quota`）が1行載っていれば3日半は数分になっていた。
4. **「HTTP ステータスが200か」だけを見る外形監視は、静かに嘘をつく。**
   5経路が3日間緑のまま、利用者だけが誤情報を見ていた。**直し方は「非200にする」ではなかった**——
   `/healthz` は暖機とヘルスチェックを兼ねるので200のままにし、代わりに**本文**へ
   `ok` / `problems` / `problem_detail` を載せて「何が壊れているか」を答えさせた（2026-09-09）。
   ステータスで落としたい用途は `/readyz`（503）、利用者と同じ公開経路を外から見るのは
   `.github/workflows/site-down-watch.yml`。**監視も人も、まず本文を読むこと。**
5. **fail-closed は今回も正しく働いた。** 欠測は設計どおりの結果であり、これを「バグ」と誤認して
   埋め戻そうとしないこと。
