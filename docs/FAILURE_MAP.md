## Q1. 沈黙死できる経路（実害の大きい順）

前提として最重要の事実: **📧（GitHub失敗メール）は「届く」が「読まれない」ことが1ヶ月事故で実証済み**。よって「📧のみ」の経路も実質的に沈黙死に準ずる。

| 順位 | 経路 | 実害 | 発覚までの推定日数（今の仕組みでの気づき方） |
|---|---|---|---|
| 1 | **Supabase の限界侵食**（実績の主因はインデックス欠落×行数増で statement_timeout を超えた瞬間の非線形反転。容量そのものは満杯まで約410日と余裕。接続数飽和も8月に実績あり） | 閾値超過の瞬間に**全経路が非線形に全滅**（収集・表示・予測・レポート全部）。128万行事故で実証 | 侵食期は**数週間〜数ヶ月完全に無音**。爆発後はheartbeat（2時間毎）→📧だが、読まれなければ「サイトが死んでる」と誰かが言うまで（実績: 発覚に丸1日規模の誤診断込み） |
| 2 | **PCスリープ/電源断**（Task Scheduler 6本の共倒れ） | 日報2便・週報・CDN温め・snapshot全停止。サイトは遅く古くなるが「死んでは見えない」 | 理論値: 翌23:30のdaily-published監視📧で1日。**実績: 10日間**（メールが読まれなかった） |
| 3 | **MEGRIBI-snapshot の「動いてるが空」**（.env.local汚染型） | 精度検証データが永久欠測（本番配信は無事だが、v2移行の判断材料が消える） | 監視ゼロ。**実績: 30日+**（手動監査で偶然発覚）。今も同型の再発を検知する手段なし |
| 4 | **監視3本＋notify経路そのものの停止**（メタ沈黙死: GHA schedule間引き悪化・PAT失効・GitHub障害） | 「異常なし」と「監視が死んでる」の区別がつかなくなる | **無期限**。check-pat-expiryが間接的に拾う可能性があるのみ |
| 5 | **warm-cdn の principal退行**（SYSTEM→Interactive） | 夜間の初回表示が1.8〜9秒に劣化。売上機会損失だが全監視が緑のまま | **無期限**（利用者の離脱でしか現れない）。実績: 2026-08-18に再発、手動発見 |
| 6 | **UptimeRobot自体の停止** | 唯一の常時外形監視が消える＋cold-start悪化。次の障害の発見が遅れる「二次沈黙死」 | **無期限**（リポジトリ側から不可視、オーナー確認要） |
| 7 | **analytics-weekly の未配信**（exit0無害設計が隠蔽） | オーナー専用機能のみ。実害最小 | **無期限**（「来ないこと」に気づく設計がない） |

## Q2. 最小の追加で沈黙死を塞ぐ案（優先順・3つ）

**案1: 通知の終着点をLINEに一本化する（最優先・全案の土台）**
- 何を作る/変える: `scripts/_ops_notify.py` と `notify-on-failure.yml` に「LINE Messaging API push」分岐を追加。push実装は `scripts/analytics_weekly_report.py` に**既にある**ので移植のみ。既存の監視3本＋notify配線済みworkflowの通知先が全部LINEになる。新SaaSゼロ。
- 検知できるようになる事故: 収集停止・日報/週報未公開・facts/cleanup失敗——**「検知はしていたのに読まれなかった」1ヶ月事故の型そのもの**を塞ぐ。
- 作業量: 半日以内（Secretsに `LINE_CHANNEL_ACCESS_TOKEN`/`LINE_USER_ID` 追加＋ヘルパー数十行）。
- 誤報リスク: 低。既存監視は調整済み（8/19にheartbeatのタイムアウト誤検知1件あり——通知文面に「2回連続で来たら本物」と書けば運用でカバー可）。

**案2: PC生存ハートビート＋「空実行」検知を既存heartbeat監視に相乗りさせる**
- 何を作る/変える: ローカルタスク（warm-cdnかsnapshot）が実行のたびにSupabaseに「生存ts＋snapshot件数」を1行書く。2時間毎に既に回っている `check-collection-heartbeat.yml` の判定を1つ増やす: 「ローカルPCのtsが24時間超で古い」「snapshotの `by_slug_count=0` が続く」→ 案1経由でLINE。
- 検知できるようになる事故: **PCスリープ（順位2）・principal退行（順位5）・.env.local汚染型の空実行（順位3）**——三重事故の主犯3つを1本で覆う。
- 作業量: 1日（書き込み側数行＋監視スクリプトに判定2つ）。
- 誤報リスク: 中。オーナーが意図的にPCを切った日に鳴る（週1回程度の許容誤報。「PC切ってたなら無視してOK」と通知文面に明記）。

**案3: 週次LINEダイジェストに「運用ステータス欄」を追加（生存証明の逆転）**
- 何を作る/変える: 既存の `analytics_weekly_report.py` の末尾に5行追記: logs行数と増加ペース（Supabase容量の侵食を数字で見せる）・最新snapshot件数・6タスクの最終成功時刻・監視3本の直近結果。
- 検知できるようになる事故: **Supabase無料枠の侵食（順位1）のような「爆発前のじわじわ系」**＋「ダイジェスト自体が来ない＝PCか配信が死んでる」という**無音の異常を『毎週来るはずの便り』の欠落に変換**——これが唯一のメタ監視（順位4・7）にもなる。
- 作業量: 半日。誤報リスク: ほぼゼロ（アラートではなく定期報告なので）。

## Q3. 監視しすぎ・無駄の指摘

1. **💬（OPS_NOTIFY_WEBHOOK）配線が多数のworkflowにあるがURL未設定＝全部no-opの死に配線**。「通知したつもり」が最も危険。案1で終着点を決めるまで、この配線は安全装置ではなく飾り。
2. **`warm-cdn.yml`（GHAバックアップ、発火率8.3%）の失敗通知**は「保険が保険として機能していないのに通知だけ持つ」状態。ワークフロー自体を残すなら通知は切ってよい（誤報源になるだけ）。
3. **UptimeRobot 5 monitor は将来削減候補**（DECISIONS #46 は「Vercel Usage が月末80%超なら5→2に削減」という条件付き決定。現時点では5本維持が前提＝過剰と断定はしない。Vercel Hobby 関数枠を消費する副作用は事実）。
4. **score_forecasts の精度劣化アラート**も未設定webhook宛＝誰にも届いていない。v2 shadow専用なので優先度は低いが、「アラート実装があるのに宛先がない」パターンの残り物。

要するに無駄の型は1つ: **チャネルが未接続なのに送信コードだけ増えている**。監視を増やすより先に、届く1本の管（LINE）に集約するのが正解。

## Q4. オーナー向け「壊れたときの一枚紙」

| 症状 | 原因候補 | 自分でできる応急処置 |
|---|---|---|
| サイトの表示が遅い（10秒級） | PCスリープでCDN温め停止 | **PCを起こしてログオン1回**。翌晩直る |
| サイトの数字が古いまま動かない | 収集停止（cron-job.org / Render） | cron-job.org画面でジョブがONか確認。ONなら放置せず相談 |
| サイトが真っ白・エラー | Render停止 or Supabase障害 | 10分待つ→直らなければRenderで「Redeploy」ボタン |
| 全部同時に死んでいる | Supabase飽和（過去2回の大事故型） | 復旧手順書どおり: cron/UptimeRobot停止→Supabase Restart→Render再デプロイ（30〜60分） |
| 日報が昨日のまま | PCスリープ or Ollama停止 | PC起動→Ollamaが動いているか確認→次の便（18時/21時半）を待つ |
| 週報が先週のまま | 同上 | 同上。木曜朝の監視メールも見る |
| GitHubから失敗メールが**1通だけ** | 一時的な失敗（自然復旧が多い） | 様子見でOK。**翌日も来たら**本物 |
| GitHubから失敗メールが**毎日来る** | 恒常的な故障 | 放置厳禁（1ヶ月事故の入口）。AIに調査を依頼 |
| 週次LINEダイジェストが来ない | PC停止 or 配信設定切れ | PCが動いているか確認。動いていれば設定点検を依頼 |
| 通知は何も来ないが不安 | 「沈黙死」の可能性 | サイトを開き**最新データの時刻**を見る。1時間以上古ければ収集が死んでいる |

---

補足（草稿からの判断上の修正点）: 草稿は📧を「気づける」側に分類しているが、1ヶ月事故の実績はこれを否定している。本回答では「📧＝実質沈黙死に準ずる」を前提に順位づけした。また草稿の沈黙死一覧はsnapshotを1位に置くが、実害基準ではSupabase侵食（全滅トリガー）とPCスリープ（利用者可視の劣化）が上位で、snapshotは「実績があるだけで実害は3番手」と判断した。

## 2. Render（Flaskバックエンド本体、gunicorn 1worker×8threads）

|---|---|
| 止まると何が起きるか | `/api/*`全滅＝フロントの店舗詳細・一覧・予測・比較ページが空箱表示（ISR/CDNキャッシュが残っている間はVercel側は生きて見えるが、キャッシュ切れ後は真っ白）。`/tasks/multi_collect`も死ぬので収集も同時に止まる（§1と連動）。日報・週報のローカルジョブも`/api/range`等を叩けず失敗する。 |

## 5. オーナーPC本体（電源/スリープ状態）— Task Scheduler 6本の共通土台

| 観点 | 内容 |
|---|---|
| 止まると何が起きるか | `MEGRIBI-*`6タスク（warm-cdn / snapshot / daily-evening / daily-late / weekly / analytics-weekly）が**まとめて全滅**。CDN温めが止まる→夜間の初回表示が遅くなる（1.8〜9秒のコールド応答に逆戻り）。日報2便・週報が生成されない→`/reports/daily|weekly/*`は前回公開分のまま古くなる（carry-over設計により空にはならないが更新が止まる）。精度答え合わせ(snapshot)が欠測する（v2 shadow専用、本番配信には影響しない）。 |
