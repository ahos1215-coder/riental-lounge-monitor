このファイルは、オーナーが「最新のアクセスを分析して」「検索クリックを見て」のように
依頼したときに、Claude / Codex どちらのエージェントが対応しても同じ手順・同じ読み方に
なるための**唯一の正本**です。Claude 向け・Codex 向けに内容を分けて書きません
（中立）。他のドキュメントからはここへリンクするだけにし、この説明の全文コピーは
置かないでください。

> **前提**: この手順は、GA4/Search Console のサービスアカウント鍵
> （`secrets/ga-service-account.json`）と `.env.local` の `GA4_PROPERTY_ID` に
> ローカルからアクセスできる**ローカル実行環境を持つエージェント専用**です。
> ブラウザ版 ChatGPT のようにローカルファイルシステムへアクセスできない環境**単体**
> では、この手順は実行できません（鍵ファイルもプロパティ設定も読めないため）。

## 最初に実行するコマンド（read-only）

```
python scripts/analytics_report.py --mode latest --days 28 --compare previous --format markdown
```

- 直近28日間を、その直前28日間と比較した Markdown サマリーを**標準出力に印字するだけ**の
  read-only コマンドです。Supabase・GA4・GSC のいずれにも書き込みません。
- セットアップが未完了（鍵ファイル未配置・`GA4_PROPERTY_ID` 未設定）の場合は、
  `docs/ANALYTICS_SETUP.md` を参照するよう案内して安全に終了します（エラーではありません）。
- 特定の指標だけでなく「最新のアクセスを分析して」のような**大まかな依頼には、まずこの
  コマンドをそのまま実行**してください。個別の期間・店舗を絞った深掘りが必要になった
  場合のみ、`--days` 等の引数を変えて再実行してください（引数の全量は
  `python scripts/analytics_report.py --help` で確認）。

## 数字の読み方（誤読を避けるための注意点）

- **GA4 の当日値は途中集計**です。当日・前日はまだ確定していないことがあるため、
  「今日は少ない」と即断しないこと。比較には確定済みの過去期間を使う。
- **Search Console のデータは実行日から遡って直近2〜3日分が未確定**です
  （Google 側の仕様。`docs/ANALYTICS_SETUP.md` にも同じ注記あり）。直近数日のクリック数が
  少なく見えても異常ではありません。
- **取得失敗を「0件」と解釈しないこと**。GA4/GSC への API 呼び出しが失敗した場合、
  `scripts/analytics_report.py` はその項目を欠落・エラーとして扱います（0件と実際の
  取得失敗は別物）。数字が0のときは、まずレポート本文にエラー・警告の記載がないか確認する。
- **「有効検索クリック」の定義**: ここでいうクリックは Search Console API の
  `clicks`（Google 検索結果ページからの実クリック数）のみを指します。GA4 側の
  「オーガニック検索」セッション数とは集計元・集計窓が異なるため、両者を同じ指標として
  混同して比較しないこと（GSC の `clicks` と GA4 の検索流入セッション数は近い値には
  なり得ますが、一致することを前提にした判断はしない）。
- **週次の単発値より28日ローリング比較を優先すること**。1週間単位の値は曜日・イベントの
  ブレが大きく、母数が小さいサイトでは特に振れやすい。傾向判断は必ず28日ローリング
  （`--days 28 --compare previous`）を基準にする。
- **母数が100未満の指標で大きな判断をしないこと**。このサイトは直近28日で数十ユーザー
  規模の小規模サイトのため、クリック数・ユーザー数が100を下回る指標は誤差の影響が
  大きい。「増えた/減った」と結論する前に、母数がその判断に耐える大きさか確認する。
- **SEO変更後は28日間の観測期間を置くこと**。施策の前後比較は、施策日から28日経つまでは
  「観測継続中」として扱い、断定的な効果判定をしない。現在のクリーン観測期間（直前の
  SEO変更の影響が出そろう期間）は **2026-08-24〜2026-09-20頃**。この期間中に発生した
  変動は、それ以前の施策の効果切り分けができない可能性があることを踏まえて報告する。
- **順位帯・検索語リストは「APIが返した上位N件」であり全件ではない**。GSCの
  `fetch_metrics`（query×page 含む）は `rowLimit` を指定して取得しており、それを超える
  順位帯・検索語は集計に含まれない。「上位N件で見た限り」という前提を付けずに
  「全クエリの傾向」であるかのように報告しないこと。
- **上に出る合計値と、その下の増減率は「期間が違う」ことがある**。`--compare previous` の
  増減率は**確定分どうし**の比較であり、レポート冒頭の合計値が集計している期間より**短い**
  ことがある（GA4/GSC の未確定日を除くため）。**増減率を読むときは、必ずそこに併記された
  比較期間の日付と日数を読むこと**。2026-09-05 に、1回の出力を「28日ぶんが◯%増えた」と
  誤読する事故が実際に起きた。ここで大事な区別: **出力された増減率の値そのものは正しかった**
  （確定分どうし＝26日と26日を比べた値として正しい）。**誤りは、28日ぶんの合計値と26日ぶんの
  増減率を、同じ期間の数字として並べて読んだことだけ**である（要求どおり28日どうしで揃えると
  ほぼ横ばいだった）。「◯%増えた」と書く前に、その % が「何日ぶん」と「何日ぶん」の比較なのかを
  本文で確認する。2026-09-06 以降は `scripts/analytics_report.py` が増減率の行ごとに実際の
  比較期間と日数を併記するので、その括弧書きを必ず読むこと。
- **機械的アクセスの混入を除くため、内訳は `country=Japan` に絞って見ること**。2026-09 時点で、
  全セッションの**およそ2割が日本国外からの機械的アクセス**（トップページ着地・滞在数秒・
  エンゲージメント0）とみられる。実利用者ではないため、ランディングページ内訳・イベント数
  などの解釈は国で絞った数字で行う。**ただし、絞ったうえでも「GA4 のユーザー数が増えた／
  減った」を結論の主語にはしないこと**（次の項目のとおり母数が小さく、増減がノイズに埋もれる）。
  国で絞るのは**無関係なアクセスが混ざったまま内訳を解釈しないため**であって、日本のユーザー数の
  増減を新しい結論にするためではない。
- **一次指標は Search Console の表示回数・クリック。GA4 のユーザー数は二次指標**。
  GA4 側は1日あたり数人規模しかなく、28日どうしの比較でも**数十%規模の変化でなければ
  統計的に検出できない**（母数が小さすぎてノイズに埋もれる）。一方 GSC の表示回数は直近28日で
  **千件台**あり、**月次の変化判定に耐えるのはこちらだけ**。GA4 のユーザー数の増減を主語にした
  結論（「先月よりユーザーが減った」等）を書かないこと。
- **オーナー自身のアクセスが数字に混ざりうる**。除外手段は**2つ**ある。
  **(a) `?dev=1`（ブラウザ単位）** — 一度開いたブラウザでのみ計測を止める。オーナーは
  2026-09-06 時点で **PC と iPhone に設定済み**（本人申告）。
  **(b) GA4 の内部トラフィック除外（IP単位）** — 自宅のグローバル IP をデータフィルタで落とす
  （手順は `docs/ANALYTICS_SETUP.md` §2-4、§0 チェックリストの項目2）。
  **ただしモバイル回線・別ブラウザ・シークレットウィンドウは、(a) はフラグが載らず (b) は IP が
  自宅と違うため、両方の網から漏れる**。母数が数十人規模なので、オーナーが数回見ただけでも
  増減率は動く。不自然な単発の山を見たら、まずこれを疑うこと。
- **クリックがどの検索語から来たのかは、ほとんど分からない**。直近28日でも、Search Console API が
  検索語を返したクリックは**全クリックのごく一部（1割に満たない）**だった（残りは Google 側の
  プライバシー保護でクエリが伏せられる）。したがって**検索語ごとの議論は「表示回数」と
  「掲載順位」に限ること**。「この検索語からのクリックが多い／少ない」という形の結論は、
  そもそもデータが存在しないので書かない。

> 上の各項目の根拠になった 2026-09-05 時点の**実数**（ユーザー数・表示回数・クリック数など）は、
> このリポジトリが public のため本文には書かない（下の「禁止事項」）。実数が必要なときは
> `plan/_local/ANALYTICS_DIAGNOSIS_2026-09-05.md`（`.gitignore` 済み＝Git 追跡外）を参照するか、
> 冒頭のコマンドを自分で実行して取り直すこと。

## UTM命名規約

現状、UTMは**アウトバウンド**（予約リンク先への付与）にのみ使われています。インバウンド
UTM（広告・提携送客などの能動的キャンペーン）は**現状打っていません**。キャンペーンを
打つときに使う命名規約は次のとおりです。

- `utm_source=x`（送客元。例: `line`, `x`, `instagram`）
- `utm_medium=social`（媒体区分）
- `utm_campaign=<施策名>`（例: `autumn_promo`）
- `utm_content=<店舗slug_YYYYMM>`（例: `shibuya_202609`）

## 計測契約（measurement contract）

分析結果を報告するときに前提として踏まえること。

- **PV定義変更日 = 2026-08-26（JST）**。この日を境にPVの計測方式が変わったため、
  **この日を跨ぐPV比較はできない（N/A として扱う）**。ユーザー数・セッション数は
  この変更の影響を受けないため、跨いでの比較は可能。
- **`report_view_canonical` = `report_view` + `report_read`**（旧イベント名からの移行互換）。
  表示・分析時にレポート閲覧数を数えるときはこの合算値を使う。**送信側は二重化しない**
  （`report_read` は過去分のみに存在し、新規発火は `report_view` に一本化済み）。
- **GA4拡張計測の「履歴イベントに基づくページビュー」は 2026-08-26 にオーナーが OFF 済み**
  （元は ON。実施記録は `docs/GA4_ADMIN_CHECKLIST.md` §1）。したがって**それ以前の期間のPVは
  SPA遷移で二重計上されていた可能性がある**ため、参考値として扱い、2026-08-26 より後の期間と
  比較しないこと（上の「PV定義変更日」と同じ扱い）。

## 禁止事項

- **実測値・検索クエリを Git にコミットしないこと**。`scripts/analytics_report.py` の出力
  （実際のユーザー数・セッション数・表示回数・クリック数・検索クエリ文言など）を、
  コミットログ・ドキュメント・テストフィクスチャに書き残さない。テストで数値例が必要な場合は
  必ず**合成データ**を使う（`docs/ANALYTICS_SETUP.md` §「動作確認」のサンプル出力も同様に
  合成データ）。**このリポジトリは public** なので、ドキュメントに書いた実数はそのまま
  外部に公開される。
  - **実数を残す必要があるときの置き場所**: `plan/_local/`（`.gitignore` の `/plan/_local/` で
    Git 追跡外）に置き、公開文書からは「実数は `plan/_local/…` を参照」とだけリンクする。
    公開文書側は**概数表現**にする（例:「直近28日で数十ユーザー規模」「全セッションのおよそ2割」
    「表示回数は千件台」）。前例: 2026-08-26（`plan/_local/ANALYTICS_R2_NUMBERS.md`）、
    2026-09-06（`plan/_local/ANALYTICS_DIAGNOSIS_2026-09-05.md`）。**同じ違反を2回やっている**
    ので、数字を書きたくなったらまずここを読み返すこと。
- **secrets の中身を開かないこと**。`secrets/ga-service-account.json` や `.env.local` の
  値そのものを読む・出力するのは禁止（ファイルが存在するかどうかの確認のみ可）。
- **分析目的の実行では書き込み系オプションを使わないこと**。`scripts/analytics_report.py`
  に書き込み系の引数が増えた場合でも、分析目的の呼び出しでは付けない
  （Supabase への保存や LINE 送信は `scripts/analytics_weekly_report.py`（週次バッチ）
  の役割であり、この runbook の対象外）。
