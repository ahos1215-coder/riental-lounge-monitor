## 4. 未決の設計論点（あなたの案と理由を。Claude 案への反対は歓迎です）

**Q1. 凍結フラグの既定値**
Claude 案はコード既定=凍結ON（env未設定でも凍結）+ yml に明示配線。
対案: 既定OFFにして yml だけで ON にする（コードの挙動が env に隠れない）。どちらが事故りにくいか。
ローカルで score を将来手動実行する場合の事故（うっかり配信を上書き）も考慮してください。

**Q2. 凍結する「値」は今日の値で良いか**
凍結は「今夜時点の blend_weights.json をそのまま固定」です。しかしその値自体、汚染された
成績表による最大7夜の産物で、日々±0.06動いていました。
対案候補: (a) 今日の値のまま（Claude 案。全店 0.47〜0.71 の中庸域にあり大外れは無い）
(b) 直近の複数夜のスコアから再計算した平滑値で固定 (c) 全店一律 0.5 に揃えて固定。
(b) は同じ汚染入力を使う点で本質改善にならない、(c) は現状からの変化が大きい、というのが
Claude の見立てですが、あなたの判断は。

**Q3. 新店のフォールバック**
凍結中に新店を出すと、キーが無いので恒久的に w=1.0（純ML）です。
(a) そのまま（現行の未採点店と同じ挙動・Claude 案） (b) キー欠損時は艦隊中央値（≈0.59）を使う
(c) 0.5。ただし (b)(c) は読み手 forecast_service.py の変更を伴い、凍結PRの範囲が広がります。

**Q4. バックアップと監視の設計（3-3, 3-4）**
この形で足りるか。shadow を毎晩書き続けること自体への異論（Storage書き込み1回/晩が増える）や、
より良い置き場所・形式があれば。

**Q5. 解除の条件を今、数値で決めておくべきか**
Claude 案は「測定契約の稼働 + preblend 有効夜の蓄積」と定性的に置いていますが、
あなたの V4 は「14夜未満は凍結・14〜27夜は収縮・28夜で店別」と数値を持っています。
凍結PRの時点で解除条件をコード or 文書にどこまで固定すべきか
（決めすぎると測定契約の設計を先取りしてしまう、決めないと恒久凍結化する）。

**Q6. 凍結と同時にやるべき/やってはいけないことの最終確認**
ロードマップ 2位（測定契約）・3位（as-of backtest + slope整合 + rain除去）との順序・干渉。
特に 3位は schema v7→v8 の3箇所同期と84本再学習を伴うため、凍結中にモデルだけ変わると
「凍結された重みと新モデルの組み合わせ」が未評価のまま配信されます。これは許容ですか、
それとも 3位の出荷時に何か手当てが要りますか。

**Q7. 反対論の最終確認（悪魔の代弁者）**
「凍結しない方が良い」と言える残りの論拠があれば正直に出してください。
例: 自動更新は壊れた基準なりに「大外れした店を翌晩補正する」保険として機能しており、
凍結するとその保険が消える——これは実データで反証できますか。

## 【統合裁定 2026-08-22】（Claude 記入・オーナー承認待ち）

Codex の回答（`plan/FORECAST_FREEZE_DEBATE_FINDINGS.md`）を精査し、新規の主張3点
（workflow に concurrency 無し／重み0件でも空 canonical を書く現行経路／`blend_weight()` の
n=0 事前値が 0.5）はすべて実コードで裏を取った。裁定は以下のとおり。

### 相違点の裁定（5件すべて Codex 案を採用）

| # | 論点 | Claude 原案 | Codex 案 | 裁定 |
|---|---|---|---|---|
| 1 | フラグの形 | boolean（既定"1"） | mode enum `frozen\|legacy_daily`＋未知値 fail-closed | **Codex 案**。boolean だと `true` 等の typo が「凍結OFF＝配信上書き」という危険側に倒れる。こちらの設計ミス |
| 2 | バックアップ | 固定名1個・存在したら skip | SHA-256 世代保存＋manifest＋read-back 検証 | **Codex 案**。「存在したら skip」は**再凍結時に古い世代を掴む実バグ**（Codex がこちらの穴を発見）。upsert が非トランザクションな点も考慮されている |
| 3 | 監視 | 存在＋shadow鮮度 | hash 不変監視（6時間毎・独立WF・自動復元なし） | **Codex 案**。「存在」だけでは別内容への上書きが緑になる。凍結の完了条件は「hash 不変」なので、監視もそれを見るのが筋。6時間毎は日次/週次と同様に間引きリスクの低い頻度 |
| 4 | 新店フォールバック | w=1.0 のまま（読み手は触らない） | キー欠損のみ 0.5／ファイル全体欠損は 1.0 維持 | **Codex 案**。0.5 は `blend_weight()` 自身の n=0 事前値と一致し、新店の初週は7日前ベースラインが無くどのみち純MLなので実挙動の変化は最小。数行で恒久純ML化の穴が閉じる |
| 5 | 凍結する値 | 今日の値のまま | 同一バイト列を hash つきで固定（再計算しない・0.5一律にしない） | **一致**（Codex がバイト列＋hash で厳密化。採用） |

### Codex 案で追加された妥当な指摘（すべて採用）

- 空 candidate の canonical 上書き禁止（現行コードは重み0件でも空 JSON を書く——実コードで確認済み）
- 広い `except` が integrity 失敗を握りつぶす現行構造の是正（最終 exit 1 へ）
- workflow への concurrency group 追加（現状無し——確認済み）と、初回配備は 06:10 帯を避ける
- 解除は `frozen → weekly`（週次・28有効夜・CI・±0.05）であり、`legacy_daily` へ戻すことを「解除」と呼ばない
- schema v8 は「凍結重み込みの composite」を同一 mask で 7〜14 有効夜 shadow 比較してから昇格。
  v7 で数えた有効夜を v8 に流用しない
- 35/56日の放置検知リマインダー（時限自動解除はしない）

### 最終案 = Codex の F-1〜F-8 をそのまま実装単位とする

Claude 原案の骨格（配信パスに触れない・shadow 継続・時限措置）は F-1〜F-8 に内包されており、
相違点はすべて安全側への強化だった。削る場合の優先順（fail-closed・hash 監視・空 candidate 禁止は
削らない）も Codex の提示どおりとする。

**未決**: オーナーの承認。承認後の実装は F-1〜F-6 を1PRで（モデル・特徴量・重み値そのものは不変、
配信値は凍結時点から1バイトも変わらないことが受入条件）。
