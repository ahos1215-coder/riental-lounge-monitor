## 0. お願いしたいこと

**このプロジェクトを初めて見た人として、率直な感想と評価をください。**

- これまでの経緯・既知の課題・私たちが出した結論は、**あえて何も書いていません**。
  先入観のない目で見てほしいからです。
- 文書に「決定事項」「絶対不変」と書いてあっても、**それが妥当かどうかは疑って構いません**。
  過去の判断が今も正しいとは限りません。
- 褒める必要はありません。**おかしいと思ったことを、思ったとおりに**書いてください。
  ただし具体的な指摘には、根拠（`ファイル:行番号` と実際に読んだ内容）を添えてください。
- 逆に「よくできている」と本当に思った点があれば、それも1〜2個は書いてください
  （どこが強みなのかを知りたいので）。

このレビューは、開発を手伝っている別のAI（Claude）とは独立した**第三者の意見**として扱います。
あなたの指摘は後で1件ずつ実際のコードで検証されます。**推測で書かず、確認したことだけを書いてください。**
確認していない場合は「未確認」と明記すれば大丈夫です。

## 1. 絶対に守るルール（違反すると事故になります）

1. **読み取り専用。** ソースコード・設定・ワークフローを書き換えないでください。
   - 例外: `plan/EXTERNAL_REVIEW_PROGRESS.md`（進捗メモ）と
     `plan/EXTERNAL_REVIEW_FINDINGS_2026-08-21.md`（最終レポート）の2ファイルだけは作成・更新して構いません。
2. **git commit / git push / ブランチ操作を一切しないでください。**
3. **秘密情報を開かない・出力しない。**
   `.env.local` / `frontend/.env.local` / `secrets/` 配下は**開かないでください**。
   このリポジトリは**公開GitHubリポジトリ**です。環境変数は「名前」だけ言及可、値は禁止です。
4. **本番に副作用のある操作をしない。**
   - 実行してよい: `git log` / `git show` / `python -m pytest` / `npx vitest run` / `npx tsc --noEmit`
   - **実行禁止**: `scripts/score_forecasts.py`、`scripts/snapshot_forecasts.py`
     （引数を受け付けない作りなので、実行すると**本番ジョブが丸ごと走ってデータベースに書き込みます**）
   - **実行禁止**: `scripts/local_report_job.py --mode publish`（本番の記事を上書きします。`--mode dry-run` は可）
   - **実行禁止**: 外部へのPOST・デプロイ・GitHub Actions の手動起動
5. 公開サイトへの **GET は歓迎**します（`https://www.meguribi.jp/` など）。実際に触ってみてください。

## 2. 進め方（外側から内側へ。この順番でお願いします）

コードから入ると「作り手の意図」に引きずられます。**まず利用者として外から見て**ください。

| Phase | やること |
|---|---|
| **P1** | **サイトを利用者として触る**（`https://www.meguribi.jp/`）。スマホ幅でも見てください。何のサイトに見えるか、誰のためのものか、使ってみてどう感じたかを書く。**この時点ではコードを読まないでください。** |
| **P2** | リポジトリを開き、構造を把握する。`CLAUDE.md` → `plan/README.md` の順に読むと迷いにくいはずです。**どこで迷子になったか・分かりにくかった箇所も記録してください**（それ自体が重要な発見です）。 |
| **P3** | コードと設計を見る。気になった点・危ういと感じた点・不具合。 |
| **P4** | 運用と事業性。続ける価値があるか、次に何をすべきか。 |
| **P5** | 最終レポートを `plan/EXTERNAL_REVIEW_FINDINGS_2026-08-21.md` に出力。 |

**各フェーズの終わりに必ず `plan/EXTERNAL_REVIEW_PROGRESS.md` を更新してください**（後述の中断・再開のため）。
途中で見つけた重要事項も、その都度そこに書き出してください（頭の中に置いたままにしないでください）。

## 3. 見てほしい観点（自由に足してもらって構いません）

答えを誘導したくないので、細かい論点は挙げません。以下は「切り口」の例です。

### P1: 利用者としての印象
- 何のサイトだと理解できたか。理解するのに何秒かかったか。
- 使いたいと思ったか。もう一度来ようと思ったか。
- 分かりにくい・信用できない・不快だと感じた点。
- スマホでの見え方。

### P2: リポジトリの第一印象
- 全体像を掴むのにどれくらいかかったか。文書は役に立ったか、それとも邪魔だったか。
- 「これは何のためにあるのか分からない」ファイル・仕組み。
- 個人開発の規模に対して、複雑すぎないか。

### P3: コードと設計
- 危ういと感じた箇所（壊れ方・エラー処理・境界値・時刻の扱いなど）。
- 設計として無理があると感じた箇所。
- テストの質（数はあるが、意味のあるテストか）。
- 実際に動かして確かめられることは確かめてください（テスト・型チェックは実行可）。

### P4: 運用と事業性（**非エンジニアのオーナーが一番聞きたい部分です**）
- この運用体制は、個人が維持できるものになっているか。
- **このプロダクトは続ける価値があるか。** 率直にどう思うか。
- 次の3ヶ月で「1つだけ」やるとしたら何か。
- やめるべきこと・捨てるべきものはあるか。

## 4. 中断したときの復帰手順（利用上限に達した場合）

あなたが利用上限で停止し、後で再開したときは、**必ず以下の手順を踏んでください**:

1. **まず `plan/EXTERNAL_REVIEW_PROGRESS.md` を読む。**
   - `STATUS: DONE` なら、レビューは完了済み。「完了済みのため作業なし」とだけ答えて終了してください。
   - `STATUS: RUNNING` または `STATUS: STOPPED` なら、`NEXT` 欄のフェーズから再開してください。
2. **完了済みフェーズをやり直さないこと。** `DONE` 欄にある内容は再調査不要です。
3. 再開したら `STATUS` を `RUNNING` に、`UPDATED` に日時を書いてください。
4. 止まりそうなとき・区切りが良いときは、**必ず進捗メモを更新してから止まってください**。
5. 全フェーズが終わったら `STATUS: DONE` にして、最終レポートのパスを記録してください。

## 5. 最終レポートの形式（`plan/EXTERNAL_REVIEW_FINDINGS_2026-08-21.md`）

日本語で。次の4部構成でお願いします。

### 第1部: 率直な総評（まずこれを読みたい）
- このプロジェクトを一言で言うと何か
- 良いと思った点（1〜3個）
- 悪い・危ういと思った点（1〜3個）
- 5段階評価をするなら（プロダクトとして／コードとして／運用として）と、その理由

### 第2部: 利用者としての感想（P1）
コードを読む前に感じたことを、そのまま書いてください。

### 第3部: 具体的な指摘（P2・P3）
実害の大きい順に。各項目は次の形式で:
```
### [重大度: 致命的 / 高 / 中 / 低] タイトル
- 場所: path/to/file.py:123
- 現象: どんな入力・状況で何が起きるか（具体的に）
- 根拠: 実際に読んだコードの引用（2〜5行）
- 実害: 利用者やオーナーにとって何が困るか
- 修正案: 最小の直し方
- 確信度: 高 / 中 / 低（確認していない場合は「未確認」と明記）
```
好みや様式の問題（命名の趣味・コメントの多い少ないなど）で、実害のないものは**書かないでください**。

### 第4部: 事業性と方向性への意見（P4）
忖度は不要です。厳しくて構いません。
