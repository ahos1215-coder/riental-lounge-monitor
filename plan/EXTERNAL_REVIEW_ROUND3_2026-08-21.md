## 0. なぜ検証をお願いするのか（今回いちばん重要な文脈）

**単体テストが緑でも、本番では全く効いていませんでした。**

あなたの指摘 F4（公開 Flask API がレート制限を迂回できる）に対して、こちらは
`/api/*` にプロセス内レート制限を実装し、専用テスト23件を書き、全て緑にして出荷しました。

出荷後に本番へ **400リクエストを8並列で7.6秒**投げたところ、**429 が1件も返りませんでした**。
守れていなかったのです。

原因は「誰からのリクエストか」を判定するキーの取り方でした。

1. 最初の実装は `X-Forwarded-For` の**先頭**を使っていた
   → 先頭は接続元が自由に付けられるため、毎回ランダムな値を送るだけで制限を素通りできる
2. そこで**末尾**（手前のプロキシが書く値）に変更した
   → それでも本番では 429 ゼロ。Render の前段が Cloudflare のため、末尾の値がリクエストごとに変わり、
     カウンタが1件も積み上がらなかった
3. Cloudflare が**必ず自分で上書きする** `CF-Connecting-IP` を最優先に変更
   → 再計測で **300通過 / 100を429**。ここで初めて効いた

**この経験から、こちらは自分たちの「直した」という判断を信用していません。**
同じ構造の穴——「テスト環境の前提（プロキシ・ヘッダ・タイムゾーン・env の既定値・
Supabase/Storage の応答形・Vercel と Render の境界）が本番と違うために、緑でも本番で効かない」——が
他の11件の修正にも潜んでいないかを、**外部の目で**確かめてほしいというのが今回の主眼です。

- 再起動のたびにカウンタが空になり、42店舗ぶんのモデルが再ロードされる（2026-07-17 のメモリ事件と同型）。
- 知りたいこと: (a) この経路は実在するか。(b) 実在するとして、プロセス内カウンタをやめるべきか
  （Upstash等の外部ストア/Cloudflare側での制限）、それとも `--max-requests` の方を見直すべきか。
  **本番での再現試験はしないでください**（DoSになります）。ローカルで同じ Procfile フラグで
  再現できるなら、その手順を教えてください。

**V4. F4の「利用者全員が1つのバケットを共有する」設計は妥当か**
- Next.js のプロキシは利用者のIPをバックエンドへ転送しないため、Render から見ると

  （守りたいのは Backend 直叩きの連打で、そちらは各自の実IPで別バケットになるため）。

- 知りたいこと: この共有バケット設計で、SNS等での突発的な流入時に**実利用者が429を食う**
  可能性をどう見るか。300/分は妥当か、上げるべきか、それとも設計自体を変えるべきか。

## 6. 中断したときの復帰手順（利用上限に達した場合）

第1・第2ラウンドと同じです。

4. 止まりそうなとき・区切りが良いときは、**必ず進捗メモを更新してから止まる**。
5. 全部終わったら `R3_STATUS: COMPLETE` にし、最終レポートのパスを記録する。
