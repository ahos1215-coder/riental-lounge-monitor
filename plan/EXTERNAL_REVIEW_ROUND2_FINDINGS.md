### A-0. 先に、競争前提を訂正する

第1回の「横断サービスは現在値中心で、履歴・予測・料金試算はほぼMEGRIBIだけ」という評価は、2026-08-21時点では正しくない。ここは私の競合調査不足だった。

[相席なう](https://aisekinow.com/) は複数ブランドを横断し、30分更新の現在値に加えて過去傾向を掲げている。[履歴ヒートマップ](https://aisekinow.com/stats/heatmap.html) は88店舗の曜日×時間帯平均を表示し、[2026年6月レポート](https://aisekinow.com/stats/reports/2026-06.html) は86店舗・66,378件を系列・エリア・曜日×時間帯で集計している。[今夜どこ行く](https://aisekinow.com/guide/today.html) はエリア・予算・気分から候補を出し、[料金ページ](https://aisekinow.com/guide/ryoukin-souba.html) は系列横断の料金比較・時間別試算を提供する。[季節予測](https://aisekinow.com/seasonal/forecast-obon.html) も公開されている。

従って、MEGRIBIの差は「横断」「履歴」「料金」「予測」という名詞の有無ではない。現在確認できる先行資産は、次の組合せである。

- 5分粒度の男女別時系列を、42店舗について同一尺度で持つ。
- 店舗別モデルが、天候、祝日・連休位置、給料日からの日数、同曜日先週、直近30分の速度を使う（`oriental/ml/preprocess.py:9-45`）。
- 19:00〜05:00を一夜として扱い、夜タイプを共通定義できる（`oriental/ml/night_type.py:1-19`）。
- 現在値、前方予測、料金、近隣店比較、LINEを、一つの「今夜どう動くか」という判断に結び付けられる。

ただし、これは永久的・構造的な参入障壁ではない。第三者競合は時間をかければ追随でき、公式は自店について入退店・待ち時間・会計など、第三者より豊かな一次データを持ち得る。公式にとって他ブランドへの送客は動機が弱い、競合にとって高頻度履歴の再収集には時間がかかる、という二点が主な障壁である。以下の「他社に作れない」は、絶対的な不可能ではなく、現時点での再現コスト・動機の差として評価する。

また「1,294,893行」は129万の独立標本ではない。5分値は強く自己相関し、実質的な単位は約1.1万の店舗夜である。給料日前後は約9回、特殊な連休はさらに少なく、2026-07-18〜08-18には部分欠測がある。訴求は「9か月連続」ではなく「2025-11-21以降、一部欠測を含む約129万行」と正確にするべきである。

#### 1位: 「今行く・待つ・店を変える」意思決定カード

#### 3位: お気に入り連動の「狙い時」LINE通知

37人・リピート5人の段階では、獲得した1人が検索なしに戻る理由が必要である。お気に入りを保存機能ではなく通知条件へ変える。ただし予測generation・鮮度・coverageのguard完成後、小規模に出す。

#### 比較ページ

2. 各店舗・エリアページへ「近隣2店と比べる」を置き、2〜3店選択済みで開く。

5. `compare_open_prefilled`、候補表示、比較後の店舗遷移、公式リンク遷移を別々に測る。

### A-4. 避けるべき方向

以下は法的助言ではない。実装・収益化前には利用規約、収集元との関係、弁護士等による個別確認が必要である。

1. 「出会える確率」「成功率」「女性の質」など、人の人数から恋愛成果・個人属性を推定しない。保有データに結果変数がなく、利用者と店舗の双方を傷つける。
2. 1〜2人の少数セルを5分精度で強調し、特定集団の追跡へ使える表示を作らない。丸め、遅延、最小セル数による抑制を検討する。個人との対応を排した統計は一般に個人情報ではないという個人情報保護委員会の説明はあるが、外部情報との組合せや少数セルは慎重に扱うべきである（[個人情報保護委員会 FAQ](https://www.ppc.go.jp/all_faq_index/faq1-q15-2/)）。
3. 雨、給料日、祝日との相関を因果として断定しない。行数ではなく独立した夜数、交絡、信頼区間を示す。
4. 「避けるべき店」「最悪店」「閉店疑惑」などの辱めるランキングを作らない。取得失敗や営業時間差が評判被害になる。
5. 店舗の同意・利用規約・法務確認なしに、生の5分データAPI、bulk dataset、個店評価商品を販売しない。創作的な選択・体系を持つデータベースには保護が及び得る（[e-Gov 著作権法 第12条の2](https://laws.e-gov.go.jp/law/345AC0000000048)）。
6. 地名×曜日×天気×店舗の薄いページを大量自動生成しない。Googleはscaled content abuseとdoorway abuseをspam policyで明示する（[Google Search spam policies](https://developers.google.com/search/docs/essentials/spam-policies)）。
7. 公式ロゴ・表示を模倣せず、「非公式」「観測元」「更新時刻」「予測であること」「訂正窓口」を常設する。出所混同を避ける必要がある（[特許庁 商標権の効力](https://www.jpo.go.jp/system/trademark/gaiyo/seidogaiyo/shotoha.html)）。
8. 料金・混雑・推薦を保証せず、根拠・限界・算定日時を示す。収益化時の優位性・効果・価格表示は合理的根拠が必要である（[消費者庁 優良誤認とは](https://www.caa.go.jp/policies/policy/representation/fair_labeling/representation_regulation/misleading_representation/)）。
9. アフィリエイトや広告報酬を推薦順位へ混ぜない。提携・広告は表示し、データ順位から分離する。
10. 欠測月を0人または通常夜として学習・集計しない。「約129万行」を生データ配布ではなく、品質管理された派生判断へ変える。
11. 店舗へ事前説明せず、個店の弱さをB2B営業資料や公開記事へ載せない。店舗向けは協調型パイロットから始め、訂正・停止経路を用意する。

## 2. 論点B〜Gへの回答

### 論点B: 事業判断

#### B-1. 「90日は信頼性リセットだけ」を維持するか

**結論: 維持しない。** 第1回の「90日を機能追加なしの信頼性リセットに限定」は取り下げる。信頼性は差別化の前提だが、それだけを90日続けても、直近28日37人・47セッションという到達母数を十分に増やせず、改善効果も観測しにくい。一方、予測の誤表示を残したまま集客だけ増やすと、弱い体験を拡散する。

信頼性を成長へ接続する経路は、単なる再訪率改善ではない。

- 正しいgeneration、鮮度、coverageを店舗ページに出し、誤表示による離脱を減らす。

### 論点D: F2・F3の重大度

#### D-1. heartbeatと5分再試行を踏まえた再評価

**結論: F2は「高」から「中」へ下げる。F3は「高」を維持するが、理由を全停止ではなくデータ完全性の長期欠損へ限定する。**

##### F2: daemon thread / 先行202は中

`.github/workflows/check-collection-heartbeat.yml:35-38` は2時間ごとに動き、夜間の全体停止を30分閾値で後追い検知する。収集自体も5分周期なので、単発のworker recycleは次周期の現在値で回復する。gunicorn timeoutを避けるための非同期化という導入意図も合理的である。

一方、`oriental/routes/tasks.py:189-198` はdaemon threadを起動した時点で202を返すため、次の時系列は残る。

1. 20:00のrequestがGunicorn workerのrecycle境界に当たる。
2. HTTP 202の後、daemonが途中終了する。
3. 20:05は新workerで成功する。
4. heartbeat時点のlatest rowは新鮮なので緑になる。
5. 20:00に失った店舗・slotはbackfillされない。

これは実在可能な欠測経路だが、単発なら範囲が狭く、長期全停止は独立heartbeatが検知する。本番でdaemon消失した実績も未確認なので、中が妥当である。

##### F3: fail/永続化の成功判定は高

heartbeatは鮮度を見ており、期待slotの完全性は見ない。`scripts/monitor/check_collection_heartbeat.py:167-177,200-204` の店舗別判定は、最新行が3日より古いかだけである。collector内部の通知も `multi_collect.py:112-116` の既定値では失敗率50%以上でしか発火しない。task側は `oriental/routes/tasks.py:41-47` で `collect_all_once()` が例外なく戻れば、`fail`件数に関係なく `status="completed"` へする。

具体的なすり抜けは次である。

1. 1日目19:00、42店舗中22店舗だけ永続化に成功し、20店舗が失敗する。
2. 戻り値は `success=22, fail=20` だが、20/42=47.6%なので既定50%alertは発火しない。
3. `tasks.py` はcompletedにする。
4. 以後も22店舗がlatest timestampを更新するため全体heartbeatは緑。
5. 失敗20店舗も最後の成功から3日未満は店舗別heartbeatが緑。
6. 71時間近く、概算20店×3夜×120slot=約7,200行を失っても全監視が緑になり得る。
7. 各失敗店舗が3日未満ごとに1行だけ偶発成功すればageはresetされ、ほぼ全欠測のまま無期限に緑になり得る。

5分再試行は現在slotを再試行するだけで、過去slotを補完しない。従って全停止のavailabilityだけなら中だが、MLと履歴という中核資産の完全性に対しては高を維持する。

**確信度: 高。** 実際に20店舗が3日欠測した履歴は未確認だが、bypass条件はコードから確定する。

#### D-2. 「真の欠陥はfail件数無視」に集約できるか

**結論: 中心は捉えるが、それだけでは不足する。** 正確な要約は次である。

> collectorの成功条件が「関数が例外なく戻ったこと」であり、「期待店舗集合の取得・永続化が完了したこと」ではない。さらに、起動response、非同期完了状態、鮮度監視、完全性監視が分離されている。

不足する点は4つある。

1. `multi_collect.py:437-443` の `HAS_SUPABASE=False` は `True` を返すため、そもそもfail件数を増やさない。docstringは挙動を説明するが、productionで禁止するruntime guardではない。これは現在本番が未設定という証拠ではないものの、設定事故時にfail検査だけでは検知できない。
2. daemonが途中終了すれば `collect_all_once()` の戻り値自体がなく、fail検査ではF2を直せない。
3. background状態をfailedにしても、起動元は既に202を受けている。durableな完了statusのpoll、または同期完了responseが要る。
4. heartbeatは店舗別期待slot数・成功率を見ない。鮮度とは別に完全性canaryが必要である。

非同期化と開発fallbackそのものを欠陥と呼ぶのではなく、production invariantと観測契約がない点を直す。

**確信度: 高。**

### 論点G: 最小実装順序

#### G-1. 統合した順序と、1本だけ選ぶ施策

**結論: 順序は「不正snapshotをpromoteしない」→「PC外から完全性をLINEへ通知」→「週次digest」。8月の長期沈黙を1本で止める施策は、PC外の2時間GHAからLINEへ届く `night-integrity sentinel` である。**

##### 1. Producer invariant / F1を先に入れる

`scripts/snapshot_forecasts.py:285-289` は正規pathへPUTした後で空を失敗判定する。これを次へ変える。

- まずimmutableなcandidate/run pathへ生成する。
- active store集合を正本に `expected_slugs == by_slug.keys()`、各店の必要slot非空を検査する。
- 空・部分なら正規 `accuracy/snapshots/{night}.json` を更新せずlast-goodを保持する。
- run manifestへ `schema_version`、`generation_id`、`night_date`、`attempted_at`、`completed_at`、`expected_slugs`、`observed_slugs`、`missing_slugs`、`status`、`canonical_promoted` を残す。
- scoreもsnapshot内の期待集合を分母にし、`expected=0`を成功にしない。

##### 2. 監視通知をLINEへ一本化し、失敗を失敗として扱う

既存通知helper/reusable workflowを、オーナーが実際に読むLINEへ接続する。未設定・non-2xxをno-op成功にせず、monitor workflowを失敗させ、GitHub emailはbackupとして残す。実装直後に意図的test通知、以後月1回の通知訓練を行う。

##### 3. 既存2時間GHAへ、PCと独立したnight-integrity sentinelを載せる

PC側は各local runの `attempt_started/finished` と件数を共有storeへ記録し、PC外GHAが次を確認する。

- PC `last_seen` / `last_attempt` の鮮度
- last-good snapshot age
- `expected == observed`、`missing == 0`

- 公開GETをbatchしてactive slug集合を確認

hard-code 42ではなくactive store集合を正本にする。単発誤報を避けるなら2回連続異常でLINE、ただし正規promotion失敗は初回から記録する。この一つの縦切りなら、PC睡眠はlast-seen、環境汚染による空実行はobserved=0/last-good staleとなり、10日・30日の無通知継続を最大数時間〜1日へ縮められる。

##### 4. 週次LINE digestは最後

canary最終成功、PC各taskのlast success、expected/actual/missing、generation、log増加率・容量を5行程度で送る。「毎週来るはずの便りが来ない」でmonitor自体の死も人間が拾える。ただし即時検知の代替ではない。

**確信度: 高。** 現在のLINE外部設定・配信成功は秘密値を開かず未確認なので、訓練を完了条件に含める。

#### G-2. F1修正と監視のどちらを先にするか

**結論: F1の書込前guardを先、同日〜翌日にsentinel/LINEを続ける。何週間も分けない。**

監視だけ先にしても、通知時点で既存良品は破壊済みである。guardは不正成果物のcanonical promotionを止める。一方、guardだけではPC停止による「何も試行されない」を検知できない。そのため順序は prevention → independent detection だが、同じ最初のmilestoneとして完了させる。

**確信度: 高。**
