## 0. このサイトにとって、予測は何か

めぐりび（https://www.meguribi.jp/）は相席ラウンジ42店（オリエンタルラウンジ37 + 相席屋5）の
混雑を5分ごとに集め、**「今夜このあと混むか」を予測して見せる**サイトです。

競合（相席なう）は履歴・曜日別ヒートマップ・月次統計・料金比較まで出していますが、
**将来予測は出していません**。つまり「今夜の条件付き予測」がこのサイトの唯一の差別化点で、
**予測が当たらなければ、このサイトの存在理由が無くなります。**

だからこそ、ここを一番厳しく見てほしいです。

## 3. 今の仕組み（読む順番のガイド）

```
利用者 → GET /api/forecast_today?store=<slug>
  → oriental/routes/forecast.py          入口・180秒 single-flight キャッシュ
  → oriental/ml/forecast_service.py      中核。夜セッション(19:00→翌05:00)の枠を作る
      1. 直近8日(最大1200行)の履歴を Supabase から取得
      2. oriental/ml/preprocess.py       24特徴量を作る（正本は FEATURE_COLUMNS）
      3. oriental/ml/model_xgb.py        ★中身は LightGBM（ファイル名だけ XGBoost の名残）
                                          男女2本のモデルを店舗ごとに持つ（42店 × 2 = 84本）
      4. _anchor_to_tonight()            今夜の実測でアンカー補正
      5. postprocess.blend_with_baseline()  ★下記
      6. postprocess.late_night_clamp()     深夜帯の上限クランプ
```

### ブレンド（ここが今回いちばん見てほしい所）

配信している値は**純粋なMLではありません**。

```
配信値 = w_ml × ML予測 + (1 - w_ml) × 季節ナイーブ（7日前・同じ時間帯の実測）
```

`w_ml` は `accuracy/blend_weights.json` から毎晩読み込みます。この重みは
**前夜までの成績から逆誤差で自動計算**されます（`scripts/score_forecasts.py::blend_weight`）:

```
w = baseline_mae / (ml_mae + baseline_mae)     直近 最大7夜 の平均
夜数が4未満なら 0.5 へ収縮 → 最後に [0.15, 0.9] にクランプ
```

実測（2026-08-22 `GET /api/forecast_today?store=shibuya`）: `blend_w_ml=0.63` /
`blended_slots=40`（全枠にブレンド適用）/ `clamped_slots=0`。

### 評価（v2 shadow パイプライン）

```
18:10 JST  snapshot_forecasts.py   その夜「配信する予測」をそのまま保存（開店前）
翌06:10    score_forecasts.py      前夜の実測と突き合わせ、MAE を出す
07:30      build_templates.py      別方式(v2=学習ゼロのテンプレ法)のテンプレを再生成
```

**v2 は答え合わせ専用**で、本番配信には一切影響しません（名前に惑わされないでください）。

### 学習

`scripts/train_ml_model.py`（GitHub Actions・日次05:30／週次月曜07:00 は Optuna 付き）
- 学習窓は **直近180日のローリング**（`ML_TRAIN_DAYS` 既定180）+ **半減期45日の指数減衰**
- 分割は**時系列順の3分割**（ランダムシャッフルなし。以前は2分割で楽観的だったのを是正済み）
- Champion/Challenger ゲートで、悪化したら昇格を却下して旧モデルを配信し続ける

## 5. こちらが自分で見つけている弱点（**反証・優先順位づけをしてほしい**）

依頼書を書くにあたって内部で棚卸ししたところ、次が出てきました。
**これらを追認するだけの回答は要りません。** 誤りの指摘、深刻度の再評価、直し方の設計をください。

### (a) 自己参照ループ — 自分の成績を自分で甘く採点している疑い

18:10 に保存するスナップショットは「**配信値**」（＝すでにベースラインを混ぜた後の値）です。
翌朝それと実測の差を取り、変数名 `ml_err` / フィールド `live_mae` として保存し、
**それを「MLの誤差」として次の `w_ml` の計算に入れています**。純ML成分の性能を独立に測っていません。

内部の近似計算では、真のML誤差 M=10・ベースライン誤差 B=2（MLが5倍悪い）のとき、
本来の望ましい重みは `w = B/(M+B) = 0.167` なのに、この再帰式の不動点は **w ≈ 0.309** に固着します。

状況証拠: 2026-08-21 に42店の実効 `blend_w_ml` を取得したところ **0.454〜0.596（平均0.539）** という
不自然に狭い帯に収まり、クランプ端点（0.15 / 0.9）に到達している店は**1店もありません**。

### (b) 重みの母数が7夜・有意差検定がゼロ

`w_ml` の計算は **店舗あたり最大7夜**にハードキャップされています（`score_forecasts.py:408` `night_dates[:7]`）。
`confidence_interval` / `p_value` / `scipy.stats` はリポジトリ全体で **grep 0件**。
それでも重みは**毎晩更新**され、翌日の配信が変わります。

### (c) 「直近40夜」の中身が水増しの疑い

2026-07-18〜08-17 の **31日間、答え合わせが完全に欠測**しています（別の事故が原因。実測で確認済み）。
ところが `summary.json` へのマージは「その夜に1店も採点できなくても1行追加する」実装のため、
`nights_count=40` は**空エントリを含んでいる可能性が高い**です。
公開APIは集計値しか返さないので、`mae_7d=13.38` が実質何夜分の平均なのか、こちらでは確定できませんでした。

**お盆（8/13-16）・夏休み本番の精度は測定ゼロ**です。年末年始・GWも未測定です。

### (d) 判定に使うベースラインが最も弱い方式

本番の `w_ml` を決めるベースラインは「**7日前の1晩だけ**の同じ時間帯の実測」という単一サンプルです。
一方で同じリポジトリの `scripts/build_templates.py` には
「**直近6夜・同じ夜タイプの中央値**」というはるかにノイズの少ない方式が既に実装されていますが、
**v2の答え合わせにしか使われておらず、本番の重み決定には使われていません**。

### (e) 学習窓180日に年末年始・GWが一度も入らない

`ML_TRAIN_DAYS=180` + 半減期45日の減衰。2026-08-22 から180日遡ると 2026-02-23 で、
**年末年始は学習ウィンドウの外**です（データとしては持っているのに）。
`holiday_block_length` / `holiday_block_position` という特徴量はありますが、
特殊期間の実例を訓練で一度も見ていないなら汎化しようがないのでは、という疑いがあります。

### (f) 損失が全部対称・不確実性を出していない

学習の目的関数は `regression`(L2) / `poisson` / `tweedie` のいずれかで、**すべて対称**です。
「空いていると予測して実は混んでいた」と「混んでいると予測して実は空いていた」は
利用者にとってコストの性質が違うはずですが、モデル化していません。

配信レスポンスは点予測のみで、**p10/p90 のような不確実性の帯はありません**（実測で確認: 区間キーなし）。
帯を計算する技術は `build_templates.py` に既にあるのに、v2 shadow の中でしか使われていません。

### (g) `next_morning_rain` がホールドアウトを楽観させている疑い

24特徴量のうち `next_morning_rain`（翌朝6-9時の降雨）は、
**学習・評価時は「翌朝に実際に観測された雨」＝未来情報**を使い、
**推論時は必ず欠損→実質0**に落ちます（コード内コメント自身が「死んだ特徴」と認めています）。
配信値には影響しませんが、**ホールドアウトの +36.7% という数字を水増ししている可能性**があります。

### (h) 42店それぞれ独立モデル

店舗をまたぐプーリング・階層モデル・店舗埋め込みは一切ありません。
客数の少ない店では「モデルが全時間帯ほぼ0を予測する崩壊」が実際に起き、
`_sparse_store_fallback()` というルールベースの後付けパッチで救済しています。

## 10. 最終レポートの形式（`plan/FORECAST_REVIEW_FINDINGS.md`）

日本語で。**コードの書き換えは不要です。設計と根拠をください。**

### 第1部: 3行の結論
「この予測は信用してよいか」「いちばん先に直すべきは何か」「その次は何か」。

### 第2部: (a)〜(h) の再判定

| 判定 | 意味 |
|---|---|
| **CONFIRMED** | 指摘どおり。深刻度も妥当 |
| **OVERSTATED** | 実在するが、こちらが深刻に見積もりすぎ |
| **REFUTED** | 事実誤認。そうはならない理由を添えて |
| **INCOMPLETE** | もっと悪い／別の問題が隠れている |

各行に **file:line と、あなたが実際に確認した方法**を添えてください。

### 第3部: V1〜V11 への回答
それぞれに **確信度**（実コードで確認した / 理論的に導いた / 推測）を添えてください。
**実装の指示は「どのファイルに、何を、なぜ」まで具体的に。**

### 第4部: 優先順位つきロードマップ
「効果 × 実装コスト」で並べてください。§2 の制約を必ず守ること。
**1つ目は必ず「1日で終わるもの」にしてください**（ソロ運用なので、大きな塊は着手されずに終わります）。

### 第5部: オーナー向けの一言（非エンジニア向け・3行）
「予測は当たっているのか」「何を直せば当たるようになるのか」。
